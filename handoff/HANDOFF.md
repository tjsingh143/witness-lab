## Isolation and architecture

Two private Lima `user-v2` networks connect the guests. Management moves to verified AF_VSOCK SSH before fault injection, independently of guest network routes. On `witness-ctl`, the runner/gateway uses lab0 `10.77.1.10` and routes `10.77.2.0/24` through `witness-field` at `10.77.1.20`. Field's dummy field0 holds `10.77.2.11/.12`; stock device services run as systemd instances. Guest nftables, no default route and no upstream DNS isolate both guests after provisioning; guest package installation opens the project's bounded temporary online window. No host routing/firewall changes are needed. Host/VPN routes overlapping 10.77.0/1/2 subnets cause a block, never a host-network edit.

Linux identity guards check Ubuntu 24.04 ARM64, VM status, hostname and pinned lab0 MAC. Guest root is necessary for tcpdump, systemd, routes and scoped faults. The field fault agent is allow-listed, accessed through a freshly generated runner key and a forced SSH command. Those private keys stay inside private lab state and never enter the return archive. A confirmed vsock management connection supplies the recovery path. Goldens share the fixed lab MACs and **are never started** beside the disposable pair.

## Deterministic experiment sequence

1. Check package/source integrity, architecture, RAM/disk/pressure; show operations and obtain informed consent. Downloads and every command are bounded. Caffeinate prevents idle sleep for the full run.
2. Establish exclusive ownership/lock and private dependencies. Refuse unrelated private-home instances or conflicting networks. Create both guests from the pinned Ubuntu image; sync/hash the source; run the actual base and role provisioning scripts twice; link fresh public keys; wait boundedly for full preflight/clock health.
3. Measure real logical/allocated disk sizes, stop the clean pair, clone both to stopped goldens, hash golden disks, restart the active pair. No result store exists in the golden snapshot.
4. Run Ubuntu units, ShellCheck and the complete adversarial acceptance verifier. Run stock commissioning, all 24 fault instances, M1–M6 with explicit stock-control evaluation and guaranteed stock restoration, then stock commissioning again. Positive results append to one main SQLite database.
5. Execute real-API F12 and gateway/F5 zero-delay and whole-response-delay controls plus split header/body 1.5+1.5 s deadline negatives. The repaired 30.0 s budget is unchanged; a negative must be error/runner, with observed row persistence within 100 ms of the limit and A23/A24 intact. It never counts as commissioning.
6. Run exact-PID TERM/F2, KILL/F2 and KILL/F5 experiments only after the active fault and both mature captures are observed. Retain natural dead-man/capture-expiry observations and orphan pcaps. Real subsequent detector baselines corroborate the killed sessions. Execute deliberate RED → reset → GREEN checks.
7. Perform **five** independent stopped-golden clone/restoration trials sequentially. Carry the new master result store forward, record distinct restoration UUIDs in both guests, provision/reset, execute full commissioning and verify exact fresh-run count, all 11 results, no retries and complete byte evidence. A repeated ordinary restart does not count. Report min/median/max variability through the production report.
8. Archive evidence, delete only the owned disposable pair, create new guests from the pinned Ubuntu image (not the goldens), provision twice, run units and full baseline/fault suites, continuing the same master evidence store. This is the recipient's genuinely fresh-VM reproduction. Golden VMs and prior evidence remain preserved.
9. Recalculate all **24** production acceptance assertions and reports from the resulting main database plus evidence bytes. Check all wrapper experiments, preserve diagnostics and shut down the disposable pair. Generate the completion report and traceability matrix automatically.

Negative/interruption diagnostics have explicitly separate stores; their overall audits can fail by design and are included in the return evidence. Their expected behavior, source stamps and integrity are separately verified. Positive campaigns/restorations/fresh-VM runs append to **one** main store; original historical stores are never imported. Tests/pytest assertions alone cannot grant acceptance.

## Resources, interruption and resumption

Resource readings are sampled during commands at approximately five-second intervals. Critical pressure, swap over 4 GiB, swap growth over 1 GiB, or free disk under **12 GiB** triggers a bounded stop and scoped recovery/shutdown, preserving the absolute **10 GiB** disk reserve with 2 GiB reaction headroom. The reserve is never traded for completion. A sudden external process consuming more than that headroom cannot be prevented by sampling; close unrelated heavy workloads. No unrelated files are removed to make space.

Before golden creation or pair replacement, additional required free disk is the **sum of both actual logical disk sizes (at least 20 GiB) + 4 GiB overhead/evidence margin + 10 GiB reserve**. Allocated sizes and formula are retained in `restore-space.jsonl`. APFS copy-on-write gets zero space credit; sparse/full-copy behavior can therefore demand more than 40 GiB initially. Heavy operations run sequentially.

Atomic checkpoints preserve every attempt, including failures. On resumption, a completed experiment is retained. An interrupted replacement resumes the same recorded creation transaction; it is not counted as another independent restore. The launcher stops exact guest runner command families, resets only identity-checked guests, collects what exists and shuts them down on exit. A killed host/power loss may prevent that handler; guest fault dead-man timers and capture expiry remain bounded. Rerun the **same** one-command message; source/ownership checks and recovery precede the remaining steps. No rows, failures, unfinished runs or earlier attempt logs are deleted to manufacture a pass. A genuine result/evidence defect can prevent acceptance and needs investigation; automatic resumption does not rewrite its history.

If the Python install prompt is declined/times out, or a resource check blocks before workspace creation, Terminal explains the blocker and no VM campaign was started. Once the coordinator exists, `output/COMPLETION_REPORT.md` contains the durable state. To regenerate a report without starting VMs: `/bin/bash RUN_ON_THIS_MAC.sh --report`. To verify package hashes without host changes: `/bin/bash RUN_ON_THIS_MAC.sh --verify` (from this directory).
