## 1. What the design predicted (written before the observation)

Phase 1 (`38e51d5`/`ad86fd3`, 2026-10-16T22:03 local) defined one writer per clock:

- witness-ctl: lima-guestagent steps the system clock to the macOS host; `chronyd -x` only **serves** that clock
  to witness-field on lab0 (`-x` = never adjust the system clock).
- witness-field: chronyd owns the clock and follows ctl (`makestep 0.1 -1`).
- REQ-04's precondition (docs/requirements.md): "field chrony has ctl selected and raw SNTP offset ctl↔field
  |x| < 100 ms". The prediction was that this gate keeps field within 100 ms of the **runner's** clock (the
  runner and gateway run on ctl and read ctl's system clock), so the ±2 s REQ-04 window has a 1.9 s margin.

## 2. Symptom

The F4 case in run 32 captured the same packets on both VMs (ctl lab0 and field lab0). The same SYN, matched by
its sequence number, carried two timestamps 1.427 s apart, over a path with a ~0.4–0.7 ms round trip:

```
ctl   capture.txt        03:51:59.359583 IP 10.77.1.10.38802 > 10.77.2.13.5020: Flags [S], seq 1754582759 ...
field capture-field.txt  03:52:00.786866 IP 10.77.1.10.38802 > 10.77.2.13.5020: Flags [S], seq 1754582759 ...
                                         -> field is +1.427283 s ahead of ctl for the same packet
```

At the same time every clock check was GREEN: run 32's session preflight logged
`PASS clock-sync SNTP offset of ctl vs field +0.000062s (|x|<0.1)`, and the gateway's READ freshness reported
`skew_s: 1.435` (device ts vs ctl clock) while still classifying the READs as fresh (inside ±2 s).

## 4. First hypothesis and why it was wrong

**Hypothesis 1: a recent clock step.** One hour earlier the same lab had shown a large clock error caused by
host sleep (09:37Z, −985 s, then a chrony step). The first checks recorded after the F4 observation are the
checks for that mechanism: the field chrony journal and both guest agents' journals since 10:40Z
(`phase3-clock-offset-f4-…105242Z.log`). (The commands and their output were logged; the reasoning was not
written down at the time, so this hypothesis is reconstructed from what was checked.)

It was refuted by that log itself:
- field chrony journal 10:40Z → now: `-- No entries --` (no step, no "System clock wrong by");
- ctl guest agent: one routine correction at 10:42:53Z of `drift was 100.398079ms` (0.1 s, not 1.4 s);
- field's guest agent cannot set the clock at all (`SyncTime: failed to set system time ... operation not
  permitted`, as designed);
- a step would also have shown up as a jump, but the offset was **constant** across the case
  (every SYN pair differs by the same ~1.427 s) and the gateway's skew was steady at 1.435–1.436 s for minutes.

**What the back-to-back wall-clock read showed instead:** field was ~1.49 s ahead of both ctl and the Mac, while
field's chrony said it was within 31 µs of its source. So field followed its source perfectly, and its
source (the time ctl **serves**) was not ctl's system clock.

## 5. Root cause (supported)

ctl's chronyd ran with `-x`, so it never touched ctl's system clock (lima-guestagent owns it). But it still
loaded `/var/lib/chrony/chrony.drift` (−80.993 ppm), a frequency estimate left over from Phase 1 before `-x`
was configured, and applied that estimate to the time it **served**. ctl's own report says so:
`System time: 1.437340140 seconds slow of NTP time` with `Frequency: 80.993 ppm slow`, i.e. chronyd's notion of
"true" time ran 81 ppm fast relative to the clock it was supposed to serve. 81 ppm × ~4.9 h since chronyd's start
≈ 1.43 s, which matches the capture offset (1.427 s) and the gateway skew (1.435 s).

Why every gate stayed GREEN: field's SNTP gate measures field against **the time ctl serves**, which field
follows within microseconds. Nothing compared the served time with ctl's system clock, which is what the
runner and gateway timestamp with. The error was in the reference, so a check against that reference could
not see it. Phase 2 data already contained the trend (field/ctl skew +5 ms in run 20, +36 ms in run 25) at
values far below any threshold. At ~0.29 s/h it would have crossed REQ-04's ±2 s window after ~7 h, producing
STALE_DATA blamed on the **device** under a GREEN preflight, which is exactly the false alarm brief section 7.2 forbids.

## 6. Fix and detection improvement

1. **Fix** (`scripts/provision_ctl.sh`, commit `4f2b2b0`): ctl's chronyd runs without a driftfile, and provisioning
   deletes an existing one. With no frequency estimate, the served time equals the system clock
   (after: `Frequency: 0.000 ppm`, `System time: 0.000000000 seconds fast of NTP time`).
2. **Detection** (`scripts/preflight.sh`, ctl check `clock-served`): the time ctl serves must equal ctl's system
   clock within 10 ms (`chronyc tracking` "System time"). Verified RED before the fix (1.4445 s) and GREEN after.
   This closes the blind spot: the gate now checks the reference itself, not only field against the reference.
3. **Re-verified in Phase 4 on fresh clones:** the Phase 2 golden clones still carried the drift file. Every
   golden restore (trials 1–5, 2026-10-17 13:03–13:12Z) logged
   `removing stale chrony drift file (-80.993317 1000000.000000); restarting chronyd` during provisioning, then
   preflight GREEN including `clock-served` (`results/logs/phase4-trial*-provision-*.log`,
   `phase4-trial*-reset-preflight-*.log`). The refreshed golden clones (Phase 4) no longer contain it: a restore
   from them was GREEN without provisioning (`phase4-newgolden-preflight-noprovision-*.log`).

## 7. Lessons

- A synchronisation check is only as good as its reference: "field agrees with its NTP server" is not "field agrees
  with the runner". The check that matters compares the two clocks the requirement compares.
- A constant offset between two captures of the same packet is a clock problem, not a network one: a 0.5 ms RTT
  path cannot produce 1.4 s, and a step would not be constant.
- Small trends in passing data (5 ms, then 36 ms) were the early warning. Every READ's raw response (with `ts`)
  and the runner's `t_send`/`t_recv` are stored per exchange (`exchanges` table), so the skew trend is queryable
  after the fact; the gateway exposes its current `skew_s` per device.
